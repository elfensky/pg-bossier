## [0.7.1] - 2026-06-28

Patch tagged `v0.7.1` on `develop` for the descent-app re-test — fixes the [#47](https://github.com/elfensky/pg-bossier/issues/47) startup deadlock (and the same lock-ordering class in `prune`). No public API change. The publish gate moves v0.7.0 → **v0.7.1**; install via the git tag until the npm publish.

### Fixed

- **`install()` / `migrate()` (and thus `ensureInstalled()` / `autoMigrate`) now retry the DDL transaction on a deadlock ([#47](https://github.com/elfensky/pg-bossier/issues/47)).** The capture-trigger `CREATE OR REPLACE` needs a heavy lock on `pgboss.job` while a *live* pg-boss holds locks on the same table in the opposite order (maintenance, queue writes, `createQueue`), so the recommended #39 "call `ensureInstalled()` right after `boss.start()`" pattern threw `deadlock detected` (SQLSTATE `40P01`) on every boot. The whole DDL block is idempotent and rolls back as a unit, so on `40P01` it now rolls back and retries with a short randomized backoff (up to 5 attempts) — it converges in 1–2. Any non-deadlock error still re-throws immediately, and the backfill (already outside the transaction, `ACCESS SHARE` only) was never the cause.
- **`prune()` now retries its `DELETE` on a deadlock too** (same `withDeadlockRetry` helper, lifted to `src/db.ts`). `prune` is fail-loud (it returns a deleted-count the caller trusts, unlike the fail-open audit writers), and its multi-row `DELETE` can deadlock against the live capture trigger upserting overlapping `pgbossier.record` rows — so a transient `40P01` there would have surfaced to the caller. Found while auditing for other instances of the #47 lock-ordering class; the fail-open writers and the capture trigger (which swallows deadlocks in its own `EXCEPTION` block) need no change.

## [0.7.0] - 2026-06-28

Minor bump tagged `v0.7.0` on `develop` — a post-0.6.1 API-consistency cleanup from a code-health (desloppify subjective) review. Two **pre-1.0 breaking** changes (the `getInputSnapshot` split and the trimmed standalone export surface); the rest is internal/cosmetic. No new capability. The first npm publish and the `develop` → `main` release stay **held pending a descent-app validation pass** — the publish gate moves from v0.6.1 to **v0.7.0**.

### Changed

- **BREAKING: `getInputSnapshot` split into two single-purpose methods.** The old dual-mode reader (`getInputSnapshot(jobId)` → wrapped result, `getInputSnapshot(jobId, attempt)` → bare value) is now two methods, each with one return shape: `getInputSnapshot(jobId, attempt): Promise<T | null>` (a specific attempt) and `getLatestInputSnapshot(jobId): Promise<InputSnapshotResult<T> | null>` (most-recent across attempts). Migration: a no-`attempt` call becomes `getLatestInputSnapshot(jobId)`. Also removes the overload-dispatch the client had to mirror.
- **BREAKING: trimmed the package's standalone value exports.** Only `bossier` and the provisioning functions `install` / `migrate` / `uninstall` are exported as callable functions now. The per-feature operational functions (`prune`, `captureHealth`, `getLiveState` / `getLiveHeartbeat` / `getLiveHeartbeats`, `subscribeEvents`, `exportRecords` / `importRecords`, `isBossierInstalled`, `pgBossDb`) are no longer re-exported from `pg-bossier` — they took pg-bossier's internal `(db, schemas, …)` calling convention, a footgun consumers shouldn't hand-thread. Reach them as `bossier()` client methods instead. All type exports are unchanged.
- **Internal: db-handle routing is now structural, not comment-convention.** The client routes each method through a `read` (fail-soft) / `write` (raw) / `probe` (raw, must-see-true-state) injector instead of hand-picking `db` / `readDb` per method, so a method can't be wired to the wrong handle by mistake. No behavior change.
- **Standardized all error/warning message prefixes to `pg-bossier:`** across `src` (some throws/warns used `pgbossier:` without the hyphen, or no prefix at all). The CLI's reserved-schema exit-64 match tolerates both spellings.

### Fixed

- **`recordDeadLetter` now short-circuits a malformed (non-UUID) job id** with a clear "malformed job id" warning, matching its five sibling job-id-keyed writers (previously a bad id degraded to a generic `db_error`).
- **The not-installed fail-soft warn-once latch is now per-client, not per-process** (`softReadDb` closure instead of a module global), so independent clients/tests in one worker no longer suppress each other's warning.

### Tests

- Replaced fixed `setTimeout` waits that gated assertions on LISTEN/NOTIFY / trigger propagation with a deadline-bounded `waitFor` poll helper (`test/wait.ts`) — removes a CI flake vector. Genuine timing tests (reconnect/backoff, idle-session-timeout) and negative "nothing fires" assertions keep their fixed waits.

## [0.6.1] - 2026-06-28

Patch release tagged `v0.6.1` on `develop` for the descent-app **v0.6.1** validation pass (install via the git tag until then). Bug fixes to the bring-your-own-connection (ORM) path and lifecycle events, plus test/CI tooling — no public API change. The first npm publish and the `develop` → `main` release stay **held pending that validation**.

### Added

- **High-volume lifecycle storm test** (`test/battle/storm.test.ts`, `npm run test:storm`). Pushes **10k–1M real jobs** through the full pg-boss lifecycle (bulk `boss.insert` → concurrent fetch → complete/fail/retry/cancel) in a single pass, verified by one aggregate SQL oracle — surfacing backlog/memory/lock-contention the bounded battle+soak path (capped ~2000/iteration by its serial send + per-job oracle) can't. Scales via `BATTLE_STORM_N` (default 0 = skipped, like the soak). New `.github/workflows/battle-storm.yml` runs a sane default on PRs and a big 100k/1M on demand (`workflow_dispatch`). Engine additions: `bulkSendWorkload` (chunked insert + cancel, plan encoded in job data), `runStormDriver` (explicit pull-pattern complete/fail), `assertStormSql` (set-based oracle).

### Changed

- **Perf scale runs** (`perf-scale.yml`): bumped the job timeout 30 → 60 min and made samples-per-method configurable via `PERF_ITERS` (default 100). A `PERF_N=1000000` run with the default 100 iterations overran the old 30-min cap (the full-scan read methods × 100 iters dominate); lower `PERF_ITERS` (~20) for 1M. CI-validated: 1M perf ~8 min (iters=20), 1M storm ~45 min — both green.
- **Test/CI tooling.** Pinned `vitest` to an exact version (`^4.1.7` → `4.1.7`) — `vitest bench` prints an "experimental feature, pin your version" advisory, so pinning is the actionable response and guards the perf tooling against silent `bench()` output drift. Migrated the test config off Vitest 4's removed `poolOptions` (`poolOptions.threads.{minThreads,maxThreads}` → top-level `pool: 'threads'` + `maxWorkers: 4`). Clarified that the battle/soak `<=2000`/iteration guidance is a *harness* limit (serial send + per-job oracle), not a pg-bossier/pg-boss engine cap.

### Fixed

- **No-row warnings now fire on the bring-your-own-connection (ORM) path.** `setProgress`, `recordInputSnapshot`, and `recordDeadLetter` detected a zero-row UPDATE via `result.rowCount`, but pg-boss's `executeSql` contract (the path used when pg-bossier runs through `boss.getDb()` — e.g. a Prisma/Kysely/Knex/Drizzle-backed pg-boss) returns only `{ rows }`, leaving `rowCount` `undefined`. So their "matched no record" / `not_found` / `conflict` diagnostics never fired on an ORM connection. All three now use `RETURNING` + `rows.length`, matching `setClaim` / `prune`. The underlying UPDATE always worked; only the diagnostics were silent.
- **`getEventsSince` now returns `claimedBy`.** It used an explicit column list that didn't include the new `claimed_by` column, so every event row came back with `claimedBy` `undefined` while every other reader populated it. Switched to `SELECT *` like the sibling readers (so a future column add can't silently drop again).

## [0.6.0] - 2026-06-27

First versioned release tagged `v0.6.0` on `develop`. The npm publish is **prepared but held pending a descent-app v0.6.0 validation pass** — the package is publish-ready (prebuilt `dist/` in the tarball, `prepublishOnly` build), but `npm publish` and the `develop` → `main` release are intentionally not yet run. Contains everything since the `v0.1.0` tag (the reposition, the trial-backlog batch, the claim API, the v0.5.0 descent-app-v0.61.0 batch, and the #11–#46 issue sweep); all pre-`0.6.0` versions were git-tag-only too.

### Added

- **Tiered retention — `exportRecords` / `importRecords`** ([#46](https://github.com/elfensky/pg-bossier/issues/46)). The export/import half of retention, pairing with `prune()` (#42): export old chronicle rows to cold storage, prune them, and import them back to reconstruct history for an audit/incident — so unbounded growth has a *lossless* answer, not just a lossy one. `exportRecords(filter?, opts?)` is an **async generator** yielding `JobRecord` batches, keyset-paginated by `seq` (stable across a long export); `importRecords(records)` re-inserts them idempotently and **non-clobbering** (`ON CONFLICT (job_id, attempt) DO NOTHING`), preserving each row's original `seq` (so re-imported historical rows stay below any live `getEventsSince` cursor and don't replay). pg-bossier owns no storage destination or format — it hands you the rows as data and takes them back (file / S3 / another DB is the consumer's choice). The only serialization wrinkle is `seq` (a `bigint`): stringify it before `JSON.stringify`; `importRecords` accepts it back as a string. New exports: `exportRecords`, `importRecords`, `ExportFilter`, `ExportOptions`, `ImportResult`.
- **`JobRecord.claimedBy`** — the read shape now includes the per-attempt claim owner (`string | null`), so `findById` / `getRetryHistory` / etc. surface `claimed_by` inline (previously only readable via `getClaim`), and the archive round-trip is lossless. Additive field.
- **Type-level test suite + `npm run test:types`** ([#16](https://github.com/elfensky/pg-bossier/issues/16)). `test/types.test-d.ts` (compiled via `tsc -p tsconfig.test.json`, wired into CI) asserts the typed read API's generics infer — `findById<In,Out>` narrows `data`/`output`, `getProgress<T>`, `getInputSnapshot<T>`, `setClaim` → `boolean` — with `@ts-expect-error` negative checks proving they are not silently `any`.
- Documented the **v1 job-payload typing pattern**: inline call-site generics (`findById<In,Out>`, `getProgress<T>`, `getInputSnapshot<T>`) with an `unknown` default; no type registry / module-augmentation layer (README § Typing your jobs) ([#13](https://github.com/elfensky/pg-bossier/issues/13)).

- **Batched install backfill + `{ backfilled }` count** ([#11](https://github.com/elfensky/pg-bossier/issues/11)). The install-time backfill (which copies jobs already in `pgboss.job` into the chronicle so you capture history predating pg-bossier) is now **batched**: it keyset-paginates `pgboss.job` by `id` in chunks of `backfillChunkSize` (new `InstallOptions` field, default 10,000) instead of one statement — one code path for every install size, so a `pgboss.job` with millions of historical jobs is copied in bounded per-statement batches, and an interrupted backfill is resumable (idempotent re-run). `install()` / `migrate()` now **return `{ backfilled }`** (new `InstallResult` type export) — how many rows were copied — and the CLI prints it. The copy stays a read-only `SELECT` that runs after the schema DDL commits, so it never blocks live pg-boss traffic. Decided: backfilled rows carry **no** `backfilled` marker column — `captured_at` ≈ install time is the signal (KISS). **API change:** `install`/`migrate` return `Promise<InstallResult>` instead of `Promise<void>` (additive — existing `await install(pool)` callers are unaffected).

- **`prune({ olderThan?, keepLastPerQueue? })` retention primitive** ([#42](https://github.com/elfensky/pg-bossier/issues/42)). `pgbossier.record` is append/upsert-only and outlives pg-boss's GC, so it grows without bound — and descent-app v0.61.0 now keeps it on a load-bearing path (claim auth + progress). `prune()` deletes chronicle rows for **fully-done** jobs (current/latest attempt terminal) bounded by `olderThan` (completion before a cutoff) and/or `keepLastPerQueue` (keep the N most-recently-completed per queue); an **in-flight job (current attempt non-terminal) is never touched** — all its rows are protected — and an eligible done job is deleted whole (all attempts). At least one bound is required (a no-arg call throws); with both, a job must violate both (intersection). Not fail-open (explicit maintenance call → errors propagate). New exports: `prune`, `PruneOptions`. **Scope note:** narrows the "no bounded retention tooling" non-goal to "no retention *policy*; a manual guarded *primitive* is allowed" — pg-bossier still never prunes on its own (no scheduler/TTL); *when* to prune stays consumer-owned (CLAUDE.md amended).
- **`autoMigrate` option + `ensureInstalled()` startup provisioning** ([#39](https://github.com/elfensky/pg-bossier/issues/39)). `bossier({ autoMigrate: true })` eagerly runs the idempotent, additive, transactional `migrate()` once at construction (mirroring how pg-boss migrates itself at `boss.start()`) so a forgotten `migrate` can't leave the now-load-bearing chronicle un-provisioned; concurrent instances racing is a safe no-op. `client.ensureInstalled()` returns the single cached migration promise — `await` it for a hard barrier before the first job; a *failed* migration is not cached, so a later call retries. Both need a real `pool` (transactional installer): `ensureInstalled()` rejects without one and `autoMigrate: true` throws at construction. The standalone `install()`/`migrate()`/CLI path is unchanged (this is opt-in).
- **`isBossierInstalled()` + fail-soft reads** ([#40](https://github.com/elfensky/pg-bossier/issues/40)). The read methods had no `try/catch`, so a `SELECT` against an uninstalled `pgbossier.record` threw a raw `relation … does not exist` — and with `getClaim` on descent-app's worker-auth path, a forgotten migrate became HTTP 500s. Reads now degrade **fail-soft** (return `null` / `[]` / zero-filled / `{ rows: [], total: 0 }` + warn once) when the schema is absent, symmetric with the fail-open writes — but **only** for `undefined_table` (`42P01`); every other error still propagates, so a schema typo or real fault is never masked. New `isBossierInstalled()` (a cheap `to_regclass` probe; named to avoid shadowing pg-boss's own `isInstalled()`) to gate on at startup. New export: `isBossierInstalled`.
- **`captureHealth({ coverage: false })` freshness-only mode** ([#43](https://github.com/elfensky/pg-bossier/issues/43)). Skips the expensive coverage `ORDER BY` over `pgboss.job` and runs only the cheap, indexed freshness query — for frequent periodic polling. `checked` / `missing` come back `null` in that mode (distinguishable from a genuine `0`).

- **Per-attempt claim owner — `setClaim(jobId, ownerId)` / `getClaim(jobId)` on the `bossier` client.** Records *which worker owns a job's current attempt* (e.g. an external pull-worker's id) in a new `pgbossier.record.claimed_by` (`text`) column. Per-attempt and forensic, so "which worker ran attempt N?" survives retries and pg-boss's `deletion_seconds` GC. `setClaim` resolves the attempt server-side (a worker needs only `job.id`) and is fail-open like `setProgress` (throws only if `ownerId` isn't a non-empty string); `getClaim` returns the `claimed_by` of the job's current (latest) attempt — matching where `setClaim` writes — or `null` if the current attempt was never claimed. A dedicated owner column — distinct from the `progress` JSON slot — so a pull-worker architecture can authorize later progress/complete/fail calls by owner without overloading progress. App-written (not trigger-captured); added to existing installs by `migrate(pool)` via `ALTER … ADD COLUMN IF NOT EXISTS` (history-preserving). New client methods: `setClaim` / `getClaim`.

- **Non-destructive in-place migration — `migrate(pool, options?)`** ([#28](https://github.com/elfensky/pg-bossier/issues/28)). Upgrades an already-adopted install to the current schema shape **without losing captured history**: `ALTER TABLE … ADD COLUMN IF NOT EXISTS` for columns a prior version's table lacks, `DROP INDEX IF EXISTS` for indexes it no longer ships, `CREATE OR REPLACE` of the capture function/trigger — touching no existing row. Replaces the old history-destroying drop+reinstall convention (which discarded exactly the records that outlive pg-boss's `deletion_seconds` GC — the reason to run pg-bossier). `install()` now applies the same additive path, so it too is upgrade-safe (a re-run on an old-shape table adds missing columns in place instead of silently skipping them under `CREATE TABLE IF NOT EXISTS`). New export: `migrate`.

- **`sendTracked(queue, data, options?)` on the `bossier` client** ([#29](https://github.com/elfensky/pg-bossier/issues/29)). A `boss.send` wrapper that pins the job id **and** stamps the same id into `data._originalJobId` in one call, so the two halves of the dead-letter lineage contract can never half-drift (the previous silent failure mode of hand-threading `{ id }` and `data._originalJobId` separately at every enqueue site). Returns the pinned job id (or `null` on a singleton dedup); pass an explicit `{ id }` to pin a known id. `sendTracked` owns `data._originalJobId` — it overwrites any caller-supplied value with the pinned id (the breadcrumb must equal the job's real id). The DLQ handler still calls `recordDeadLetter` (only it knows both ids), reading the source id back from `data._originalJobId`.

- **`captureHealth(opts?)` on the `bossier` client** ([#31](https://github.com/elfensky/pg-bossier/issues/31)). An app-level signal for the otherwise-silent fail-open capture path: returns `{ lastCapturedSeq, lastCapturedAt }` (chronicle freshness — alarm on staleness) plus `{ checked, missing }`, a coverage check counting how many of the most-recent live `pgboss.job` rows have no `record` (default 1000-job sample, `{ sampleLimit }` to widen). The coverage half is **not** O(1) — finding the most-recent N is an `ORDER BY created_on DESC LIMIT` over `pgboss.job` that scans/sorts proportional to the live-job count (`sampleLimit` bounds the result, not the scan), so call `captureHealth()` periodically (cron), not on a hot path; the freshness half is cheap. Observability only — capture stays fail-open. New export: `captureHealth` + the `CaptureHealth` type.

- **`getLiveHeartbeats(ids)` on the `bossier` client** ([#34](https://github.com/elfensky/pg-bossier/issues/34)). A batched live heartbeat read — one query for many jobs, returning a `Map` keyed by every requested id (`Date | null`) — to avoid an N+1 loop of per-row `getLiveHeartbeat` on a dashboard. Reads `pgboss.job` directly (Transitional tier) because pg-boss's `findJobs` takes a single id; LIVE and non-forensic like `getLiveHeartbeat`. New export: `getLiveHeartbeats`.

- **`{ live: true }` option on `countByState` / `countByQueue`** ([#27](https://github.com/elfensky/pg-bossier/issues/27)). These methods count the chronicle by default, which retains jobs pg-boss has deleted — an all-time **superset** of live queue depth that surprised the trial's "by state / by queue" dashboards on adoption. `{ live: true }` counts the live `pgboss.job` table instead (drop-in parity with the raw `pgboss.job` counts those dashboards replaced). New `CountFilter` type export. The default (all-time) behaviour is now called out in the method JSDoc and README, not just a scorecard footnote.

- **Single-surface re-exports.** `pg-bossier` now re-exports pg-boss's entire public module surface (`export * from 'pg-boss'`) — the `PgBoss` class, the `fromPrisma` / `fromKnex` / `fromKysely` / `fromDrizzle` ORM adapters, and every pg-boss type — alongside pg-bossier's own API. A consumer imports everything from one package: `import { PgBoss, bossier, fromPrisma, getLiveState, type JobWithMetadata } from 'pg-bossier'`. pg-bossier's own named exports take precedence on any name conflict (ESM `export *` semantics). This is the module-level half of the "complete single surface" facade.

- **Live runtime-state reads — `getLiveState(jobId)` / `getLiveHeartbeat(jobId)`.** Closes the heartbeat/expiry gap that previously forced consumers back to raw `pgboss.job` SQL, without merging the live and durable surfaces. `getLiveState` returns `{ livePresent, liveReadAt, recordState, job }`: it reads pg-boss's **current** runtime row via `boss.findJobs(queue, { id })` (the queue comes from the durable record, so the lookup is scoped to one partition — no cross-partition scan), and is **explicitly non-forensic** ("what pg-boss says now", not history). When no live row exists, `recordState` (from the durable chronicle) disambiguates a genuinely-done job (`completed`/`failed`/`cancelled`) from a brief retry DELETE+INSERT gap (`active`/`retry`/`created`) — so a polling UI never flashes a false "not found". `getLiveHeartbeat` is a convenience returning just the live `heartbeatOn` (`Date | null`). New exports: `getLiveState`, `getLiveHeartbeat`, and the `LiveState<T>` type. Works without a `pool` (routes through the resolved `db` + pg-boss's own API). The forensic question "when did a now-dead job last beat?" is deliberately **not** answered here (the live row is gone) — a separate opt-in capture would be needed.

- **Bring-your-own connection / ORM.** `bossier()`'s `pool` is now **optional**: when omitted, pg-bossier's read/write methods run through pg-boss's own DB handle (`boss.getDb()`), so a consumer running pg-boss with a Prisma/Knex/Kysely/Drizzle adapter (pg-boss's `db` constructor option) never has to hand pg-bossier a separate `pg.Pool`. New `BossierDb` interface (the minimal `query` surface, satisfied structurally by `pg.Pool`) and `pgBossDb(boss)` helper are exported; a new `db?: BossierDb` option overrides the default resolution (`db` → `pool` → `boss.getDb()`). The query-only modules (`read` / `progress` / `terminal-detail` / `dead-letter` / `input-snapshot`) now take a `BossierDb` instead of a `Pool`. **Exceptions that still need a real connection:** `subscribeEvents` (LISTEN/NOTIFY needs a dedicated pg connection that ORM adapters don't expose — it now throws a clear error if the client was built without a `pool`) and `install` / `uninstall` (transactional DDL — keep taking a `Pool`, typically via the CLI). Back-compatible: existing `bossier({ boss, pool })` callers are unaffected.

- **Capture three immutable `pgboss.job` config columns into `pgbossier.record`** — `priority`, `retry_limit`, `singleton_key`. The capture trigger and the install backfill now mirror them, and `JobRecord` exposes them as `priority` / `retryLimit` / `singletonKey` (`number | null`, `number | null`, `string | null`). This lets descent-app's `getJobById` / `getRecentJobs` / `getJobsPaginated` read fully from pg-bossier (the admin table's "Pri" and "Retries X/Y" cells and the detail modal's `singletonKey`) without a residual raw `SELECT` against `pgboss.job`. Reopens the 2026-06-20 pre-trial decision (b) — the trial surfaced the concrete need (a blank Pri column), the documented trigger for revisiting [#26](https://github.com/elfensky/pg-bossier/issues/26). Scoped deliberately: the other two of the five metadata columns stay uncaptured — `heartbeat_on` is live runtime state the `UPDATE OF state` trigger structurally can't track (and only meaningful for in-flight jobs, whose `pgboss.job` row still exists), and `expire_seconds` is selected-but-never-rendered. These three are immutable job config (set once at `send()`), so they're written only on the INSERT and never re-written on a state transition. **0.x schema change: existing installs run `migrate(pool)`** — the new non-destructive in-place upgrade ([#28](https://github.com/elfensky/pg-bossier/issues/28)), which adds these columns via `ALTER TABLE … ADD COLUMN IF NOT EXISTS` while preserving captured history (superseding the earlier drop+reinstall guidance); the backfill repopulates config for every job still present in `pgboss.job`.

- Seeded chaos/battle-test harness (`test/battle/`): drives N jobs of varied
  shape/outcome through concurrent push + pull workers and asserts the
  `pgbossier.record` chronicle stays faithful per job, plus forensic-delete
  survival, fail-open (audit-path outage), and a gated connection-kill phase
  (`BATTLE_CHAOS_FULL=1`). Reproducible via `BATTLE_SEED`; tunable via `BATTLE_N`.
- Long-running soak harness (`test/battle/soak.test.ts`, `npm run test:soak`):
  reuses the battle engine in a wall-clock loop (`BATTLE_SOAK_MINUTES`) of
  bounded-`N` storms, asserting the per-job oracle, forensic-delete survival,
  periodic audit-outage fail-open recovery (`BATTLE_SOAK_OUTAGE_EVERY`), and a
  strictly-ascending event-seq finale every run. Opt-in: at `0` minutes the file
  is skipped and boots no container, so the default suite pays nothing.
  Connection-kill recovery is intentionally excluded (it surfaces unhandled
  pg-boss socket `error`s — kept in the gated Phase D). Manual-only CI workflow
  `.github/workflows/battle-soak.yml` (`workflow_dispatch`, inputs:
  minutes / n / seed).

### Changed

- **`setClaim` is now compare-and-set and returns `Promise<boolean>`** ([#41a](https://github.com/elfensky/pg-bossier/issues/41)). It writes `claimed_by` on the current attempt **only if** that attempt is unclaimed or already owned by `ownerId`, and returns whether `ownerId` holds the claim afterwards (`true` = won/owns it, `false` = lost to another owner / unknown job / not installed). Two workers racing → exactly one `true`; idempotent for the owner. Lets a pull-worker treat the marker as authoritative without relying on pg-boss's `fetch()` to serialize claimants. **Pre-1.0 signature change** (was `Promise<void>`); the rowCount-0 "is pg-bossier installed?" warn is dropped (a no-match is now a normal CAS outcome — use `isBossierInstalled()` to detect a missing install). #41(b) (`getClaim` current-attempt scoping) was already delivered in v0.4.1.
- **`CaptureHealth.checked` / `.missing` widened to `number | null`** ([#43](https://github.com/elfensky/pg-bossier/issues/43)) — `null` when the coverage check was skipped via `{ coverage: false }` (see Added), distinguishable from a genuine `0`.
- **Non-goal narrowed: "no bounded retention tooling" → "no retention _policy_; a manual guarded _primitive_ is allowed"** ([#42](https://github.com/elfensky/pg-bossier/issues/42), see `prune` under Added). pg-bossier still never prunes on its own (no scheduler/TTL) and *when* to prune stays consumer-owned; it just no longer makes consumers hand-write `DELETE`s. CLAUDE.md § Non-goals amended.
- **`install()` is now additively upgrade-safe** (see `migrate` under Added, [#28](https://github.com/elfensky/pg-bossier/issues/28)): its DDL transaction adds missing columns (`ALTER … ADD COLUMN IF NOT EXISTS`) and drops obsolete indexes (`DROP INDEX IF EXISTS`) in place, so re-running it on an install from a prior version upgrades the schema without the old `CREATE TABLE IF NOT EXISTS` no-op silently skipping new columns. Still non-destructive and idempotent; a fresh install is unchanged.
- **`countByState` / `countByQueue` documented as all-time-by-default** ([#27](https://github.com/elfensky/pg-bossier/issues/27)). The "counts include jobs pg-boss has deleted, so this is a forensic superset of live queue depth" caveat — previously only a scorecard footnote — is now in the method JSDoc (editor hovers) and README. Behaviour unchanged; pass `{ live: true }` (see Added) for a live count.
- **Packaging: added `prepublishOnly: "npm run build"`** so the npm tarball is built once on the publisher's machine ([#32](https://github.com/elfensky/pg-bossier/issues/32)). `prepare` is kept for now (git-URL installs still build on install until the package is published); the README install section now warns that the git-URL path needs install scripts allowed (fails under `npm ci --ignore-scripts` / allow-scripts gating). The durable fix is the npm publish, which ships a prebuilt `dist/` with no build-on-install.

The `GetEventsSinceOpts` type export is removed. Pre-1.0 signature simplification; a future second option can reintroduce an options object without a stability cost while still on `0.x`.

Removed the speculative ALTER-based "upgrade path" and its test — no pre-`seq` version ever shipped, so there was no in-place upgrade to support (0.x schema changes are drop+reinstall). Resulting schema is identical.

### Removed

- **Dropped the unused `data` / `output` / `input_snapshot` GIN indexes** from `pgbossier.record`. No read method runs a JSONB `@>` containment query on those columns (only `terminal_detail` does — its `record_terminal_detail_gin` stays, serving the DLQ-lineage lookup), yet each GIN index write-amplified *every* capture-trigger row against the per-event performance budget. Validated as the one clear cut by a 5-model goal-alignment debate (the containment-search method that would use them is explicitly out of scope). The columns and their data are untouched — re-add a specific index in one line if/when a containment-search method is scoped. **0.x schema change:** `migrate(pool)` drops the obsolete indexes in place (or the standard `uninstall()` + `install()` on a fresh DB).

### Fixed

- **`getClaim` is now scoped to the job's current (latest) attempt** instead of returning the most-recent non-null `claimed_by` across *all* attempts (`v0.4.0`). The old cross-attempt read could return a stale owner from a prior failed/retried attempt: on a retried job whose current attempt was unclaimed, `getClaim` returned the previous attempt's owner, which broke the documented owner-equality authz pattern (`if (getClaim(id) !== workerId) throw`) both ways — it rejected the legitimate new worker and could authorize a zombie worker from a dead attempt. `getClaim` now reads `claimed_by` of `max(attempt)` (where `setClaim` writes), so a fresh retry attempt reads back as unclaimed (`null`) until its worker calls `setClaim`. Also: `setClaim` short-circuits a malformed (non-UUID) `jobId` to a clear "malformed job id" warning + no-op, instead of the prior confusing Postgres `uuid`-cast error in its fail-open catch.

- **`build` now cleans `dist/` first**, so deleted sources don't leave stale compiled artifacts in the published tarball. A `prebuild` step (`fs.rmSync('dist')`, stdlib-only, cross-platform) runs before `tsc`; previously a leftover `dist/record.js` (from the removed `src/record.ts`) was still packed by `npm pack` / would ship on publish.

- **pg-bossier's `subscribe` no longer shadows pg-boss's own pub/sub `subscribe`.** The lifecycle-event subscription is renamed `subscribe` → **`subscribeEvents`** (on the `bossier` client and as the standalone export). The proxy resolved pg-bossier's `subscribe` first, so pg-boss's native pub/sub `subscribe(event, name)` was unreachable through the client while `publish` / `unsubscribe` still forwarded — a half-broken surface, and `PgBoss & BossierMethods` intersected two incompatible `subscribe` signatures. After the rename, every pg-boss method (including `subscribe` / `publish` / `unsubscribe`) forwards cleanly and `subscribeEvents` carries pg-bossier's events. The collision guard is now driven by the exported, complete `BOSSIER_METHOD_NAMES`: the proxy routes *only* those names, so a method can't be quietly dropped from the list to keep the guard green — which is exactly how the original shadow hid. Pre-1.0 breaking rename: callers of `client.subscribe()` / the `subscribe` export switch to `subscribeEvents`.

- **`recordTerminalDetail` is now fail-open like every other audit writer** ([#36](https://github.com/elfensky/pg-bossier/issues/36)). It was the only write method that wrapped its `db.query` in *no* `try/catch` and skipped the `UUID_RE` guard — so a transient DB error (connection drop, pool exhaustion) thrown while a worker *classified a failure* propagated into the consumer's job handler, and a malformed (non-UUID) `jobId` raised a raw `invalid input syntax for type uuid`. Both violated issue #1's "audit writes are fail-open" constraint that `setProgress` / `setClaim` / `recordInputSnapshot` / `recordDeadLetter` already honor. Now a DB error is logged via `console.warn` and swallowed, and a malformed id short-circuits to a clear warning + no-op. Validation throws (non-plain-object payload, missing failure `class`, non-serializable detail) are unchanged — those are programmer errors. A state-mismatch / wrong-`(jobId, attempt)` UPDATE matching zero rows stays a deliberate silent no-op.
- **`subscribeEvents` no longer leaks pooled connections on a flapping DB** ([#37](https://github.com/elfensky/pg-bossier/issues/37)). Three lifecycle gaps in the LISTEN/NOTIFY client are fixed: (1) `open()` now releases the acquired `PoolClient` if setup fails *after* `connect()` (e.g. the `LISTEN` query throwing) — previously the client was orphaned, and since the reconnect loop retries through `open()` it leaked one connection per attempt until the pool exhausted; (2) the internal `reconnectCancellers` array now drops each timer's canceller once it fires, instead of growing unbounded for the process lifetime across reconnects; (3) an `AbortSignal` firing *during* `open()` now tears down the half-opened subscription instead of orphaning a live `LISTEN` client on an already-closed instance. Also hardened: internal `error` dispatch no longer recurses on a throwing `error` listener and no longer trips Node's "`emit('error')` with no listener throws" process-crash footgun (a fail-open audit layer must never crash the host), and `warning` / `connected` listener exceptions are isolated like the job-event listeners.
- **`engines.node` raised to `>=20.4.0`** ([#38](https://github.com/elfensky/pg-bossier/issues/38)). The previous `>=18.3.0` floor (set by `parseArgs`) was below where `Symbol.asyncDispose` exists (Node 20.4.0), which `BossierEvents` implements for `await using`. On Node 18 the computed key `[Symbol.asyncDispose]` silently coerces `undefined` to the string `"undefined"`, so `await using` disposal was a no-op and the `LISTEN` connection never released — while the package advertised support. The floor now matches the code. `.close()` was (and is) unaffected on every supported Node.

- **CLI no longer aborts on a non-URL connection string** ([#44](https://github.com/elfensky/pg-bossier/issues/44)). `bin/pgbossier.js` parsed the DSN with `new URL()` only to pretty-print the destination before connecting; a libpq keyword/value DSN (`host=… dbname=…`) threw `Invalid URL` and killed the command (exit 2) from that cosmetic line, before any connect was attempted. The print is now wrapped in `try/catch` and degrades gracefully (omits `host`/`database`, and never echoes the raw string, which could carry a password) so the *connect* path decides whether the DSN is usable.
- **Docs synced with code** ([#45](https://github.com/elfensky/pg-bossier/issues/45)): `CLAUDE.md` corrected from `fileParallelism: false` (one container per file) to the actual `fileParallelism: true` / `maxThreads: 4` (changed in `e5614e7` for [#24](https://github.com/elfensky/pg-bossier/issues/24)), and the Node requirement in `CLAUDE.md` + `README.md` updated from `≥ 18` to `≥ 20.4` to match the v0.4.2 engines floor.

### Removed

- **`recordPatch` and the `RecordPatch` type.** The general-purpose patch writer had narrowed over time to a single writable column (`input_snapshot`) — the same column `recordInputSnapshot` already owns — making it redundant duplicate tooling. `recordInputSnapshot` is now the **sole** input-snapshot writer. `recordPatch`'s only unique behavior, clearing the column to SQL `NULL` via `{ input_snapshot: null }`, was dropped as unused (descent-app's domain audit table owns provenance, so `input_snapshot` is opt-in and rarely written); re-add to `recordInputSnapshot` if a clear path is ever needed. ### Fixed

- **README dead-letter contract corrected.** The documented `_originalJobId` pattern put the self-identifying id only on the job's `data`, not as the job's *actual* id — but `recordDeadLetter` keys on pg-boss's real job id (via the chronicle), so as written it would silently no-op (`reason: 'not_found'`) and never record the lineage. The examples now also pass `{ id: sourceId }` to `send` and explain that both halves (the `id` option *and* the `data` field) are required. Verified end-to-end by a new test against pg-boss's native dead-letter routing.
- **`install()` no longer freezes a live pg-boss queue while backfilling.** The backfill `INSERT … SELECT FROM pgboss.job` previously ran inside the same transaction as `CREATE`/`DROP TRIGGER` on `pgboss.job`, so the trigger DDL's lock (DROP: `ACCESS EXCLUSIVE`, CREATE: `SHARE ROW EXCLUSIVE`) was held for the entire backfill — blocking every pg-boss queue write (and read) for as long as the backfill ran on a large `pgboss.job`. The DDL now commits first (trigger goes live, lock releases); the idempotent `ON CONFLICT DO NOTHING` backfill runs afterward, where its `SELECT` takes only `ACCESS SHARE` and never blocks pg-boss. DDL remains atomic; a failed backfill is safely completed by re-running `install()`. Surfaces a mis-framing in issue [#11](https://github.com/elfensky/pg-bossier/issues/11) (the risk is the trigger DDL lock, not the backfill SELECT's own lock).
